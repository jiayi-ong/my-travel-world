SIMULATION MODULE — DESIGN NOTES
=================================

1. WHY SimClock IS A VALUE OBJECT
----------------------------------
SimClock is designed as a Value Object in the Domain-Driven Design sense: it encapsulates
a single piece of state (the current simulation datetime) and exposes only controlled
mutation through well-named methods (tick(), advance_to(), reset()). It has no references
to other domain objects and produces no side effects beyond updating its own internal time.
This makes SimClock trivially testable — you can create one, advance it, and assert its
state without any mocking or dependency setup. It also makes the simulation time value
portable: a SimClock can be passed around, inspected, or serialized without risk of
inadvertently triggering world state changes.

2. WHY TickEngine IS SEPARATE FROM SimClock (Single Responsibility Principle)
-------------------------------------------------------------------------------
SimClock knows only one thing: what time it is and how to advance. TickEngine knows
only one thing: how to coordinate a tick across all layers. Merging them would violate
Single Responsibility — the combined class would need to know both how simulation time
works AND how to iterate over world layers and dispatch updates. Separating them means:
- SimClock can be tested independently of any WorldState.
- TickEngine can be tested with a mock SimClock and mock layers, without real time logic.
- Future changes to the tick dispatch logic (e.g., parallel updates, priority ordering)
  do not touch clock logic, and vice versa.

3. DELIBERATE IN-PLACE MUTATION IN tick() VS IMMUTABLE SWAP ELSEWHERE
-----------------------------------------------------------------------
The dominant pattern elsewhere in the codebase (WorldState construction, layer loading)
uses immutable data structures and functional-style transformations, returning new objects
rather than mutating existing ones. The tick() method intentionally breaks this pattern
for a specific reason: simulation ticks are designed to be high-frequency operations
(called hundreds or thousands of times during a simulation run). Creating a fresh copy
of the entire WorldState — which may contain multiple large layers with thousands of
entities — on every tick would impose unacceptable memory pressure and GC overhead.
Instead, layers are mutated in-place during tick(). This trade-off is explicitly
documented here and in tick_engine.py's docstring so future contributors understand
it is a deliberate performance decision, not an oversight.

4. HOW FROZEN LAYERS INTERACT WITH THE TICK ENGINE
----------------------------------------------------
BaseLayer defines a tick_update(current_time: datetime) method. For layers where the
frozen flag is True, tick_update() is a no-op — it returns immediately without modifying
any internal state. TickEngine does not need to check the frozen flag itself; it simply
calls tick_update() on every layer and lets each layer's own implementation decide
whether to act. This preserves encapsulation: the frozen/unfrozen decision belongs to
the layer, not to the engine. The practical effect is that frozen layers (e.g., a static
GeoLayer snapshot) incur only a trivial function-call overhead per tick, which is
acceptable. If profiling ever shows this to be a bottleneck, TickEngine.tick() can be
optimized to skip frozen layers by checking the flag before dispatching, since the
BaseLayer.frozen attribute is part of the public interface.

5. FUTURE EXTENSIBILITY: DISRUPTION EVENTS HOOKING INTO THE TICK ENGINE
------------------------------------------------------------------------
Planned disruption events (flight cancellations, venue closures, weather disruptions)
will integrate with the tick engine via an event queue attached to WorldState. The
proposed design is:
- WorldState holds a priority queue of ScheduledEvent objects, each with a trigger_time
  and an apply(world_state) callback.
- At the start of each tick(), after advancing the clock, TickEngine checks the event
  queue and pops all events whose trigger_time <= clock.current_time, calling apply()
  on each before dispatching tick_update() to layers.
- This keeps disruption logic out of individual layers (layers don't know about events)
  and out of TickEngine's core logic (the queue is processed in a pre-tick step).
- Events can be generated by the world generator (seeded disruptions), by the
  EconomicsLayer (demand spikes triggering price surges), or injected externally via
  the /world/inject_event API endpoint for researcher-driven experiments.
